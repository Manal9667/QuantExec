# Market Data Format and Schema

## Overview

This document specifies the CSV market data format consumed by `CsvMarketSource` and produced by external adapters. All data is normalized into the `MarketState` structure before reaching the matching engine or execution strategies.

## Required CSV Schema

A valid CSV file must include these **required columns** (in any order):

```
timestamp_ms, last, bid, ask, bid_size, ask_size, volume
```

### Required Columns

| Column | Type | Unit | Description |
|--------|------|------|-------------|
| `timestamp_ms` | uint64 | milliseconds | Time since epoch (Unix timestamp). Must be **strictly increasing** (no duplicates, no backward steps). |
| `last` | double | currency | Last trade price. Must be positive and finite. |
| `bid` | double | currency | Best bid price. Must be positive and finite. |
| `ask` | double | currency | Best ask price. Must be positive and finite. |
| `bid_size` | uint64 | quantity | Volume available at the best bid. Must be non-negative. |
| `ask_size` | uint64 | quantity | Volume available at the best ask. Must be non-negative. |
| `volume` | uint64 | quantity | Cumulative total volume for the symbol (session open). Must be non-negative. |

### Validation Rules for Required Columns

1. **Timestamp monotonicity**: `timestamp_ms` must strictly increase. Duplicate or backward timestamps are rejected.
2. **Price finiteness**: `last`, `bid`, `ask` must not be NaN or infinity.
3. **Bid-ask relationship**: `bid ≤ ask`. If `bid > ask`, the row is invalid.
4. **Positive prices**: All prices must be `> 0.0`.
5. **Quantities**: `bid_size`, `ask_size`, `volume` must be non-negative (`>= 0`).

## Optional Columns

### `bar_volume` (optional)

| Column | Type | Unit | Description |
|--------|------|------|-------------|
| `bar_volume` | uint64 | quantity | Volume accumulated during this event / bar only. Defaults to 0 if omitted. |

**Use case**: VWAP strategy can use `bar_volume` to weight slices to the market's volume profile within a timeframe.

### Depth Columns (optional)

| Column | Type | Format | Description |
|--------|------|--------|-------------|
| `bid_depth` | string | `price:qty\|price:qty\|...` | Multiple bid levels, best first. |
| `ask_depth` | string | `price:qty\|price:qty\|...` | Multiple ask levels, best first. |

**Format**: Pipe-delimited (`|`) levels; each level is `price:qty`.

**Example**:
```
bid_depth: 100.0:100|99.99:200|99.98:150
ask_depth: 100.01:50|100.02:200|100.03:300
```

**Parsing**:
- If `bid_depth` is present, it is parsed into a vector of `BookLevel` objects.
- The first level (best) becomes the top-of-book bid; subsequent levels are stored for matching.
- If parsing fails for any level, that level is skipped; incomplete depth is accepted.
- If no depth columns are present, only top-of-book (`bid`, `ask`, `bid_size`, `ask_size`) is available.

## Complete Example

```csv
timestamp_ms,last,bid,ask,bid_size,ask_size,volume,bar_volume,bid_depth,ask_depth
1000,100.01,100.0,100.02,212,579,120,120,100.0:212|99.99:425,100.02:579|100.03:414
2000,99.99,99.98,100.0,252,546,359,239,99.98:252|99.97:756,100.0:546|100.01:579
3000,99.97,99.96,99.98,416,216,416,57,99.96:416|99.95:347,99.98:216|99.99:411
```

## Data Provenance

### Synthetic vs. historical data — how this project distinguishes them

Every dataset in this project is one of exactly two kinds, and the
distinction is enforced by tooling, not just a comment:

| Kind | What it is | How you can tell |
|---|---|---|
| **synthetic** | Generated by `datasets/generate_sample.py`. Deterministic, used for unit tests and CI. Not evidence about how any real algorithm would have performed. | Its manifest (see below) has `"data_type": "synthetic"` and no provider/source fields. |
| **historical** | Real recorded market data from a named provider, with a documented acquisition method, license, timezone, and resolution. | Its manifest has `"data_type": "historical"` and full provenance fields — the manifest tool refuses to write a `"historical"` manifest without them. |

**Current status of this repository: one historical dataset is bundled,
alongside the synthetic fixture.**
`datasets/historical/AAPL_2024-01-03_0930-1030ET.csv` is real AAPL
top-of-book quote data from Alpaca's IEX feed, with a full provenance
manifest (`data_type: historical`, provider, source URL, license,
timezone, SHA-256, and documented cleaning steps). It has real, disclosed
gaps — it is **quote-only** (`last` is the quote midpoint and `volume` is
`0` on every row, because no trade-print data was acquired), resampled to
one row per minute, and single-venue (IEX, not consolidated SIP). Those
gaps are spelled out in `LIMITATIONS.md` §1 and in the manifest's own
`notes` field. `datasets/sample_synthetic.csv` remains the synthetic
fixture used by tests. Nothing here should be read as claiming a verified
historical dataset exists unless its manifest says so — which, for the
AAPL file, it does.

### Dataset manifest and validation tool (`scripts/build_dataset_manifest.py`)

Before any CSV is treated as a usable dataset, run it through the manifest
tool. It performs every check listed in the "Validation Rules" sections
above (missing columns, malformed rows, duplicate timestamps,
non-monotonic timestamps, invalid bid/ask, negative price/quantity,
non-finite values) independently of `CsvMarketSource`, and it **fails
loudly** — printing every problem found, with row numbers — rather than
silently producing an unloaded source the way `CsvMarketSource::ok()` does
three layers away from the actual bad row.

```bash
# Synthetic / generated data - no provenance fields required
python3 scripts/build_dataset_manifest.py datasets/sample_synthetic.csv \
    --data-type synthetic --symbol SYN \
    --resolution "synthetic top-of-book ticks" \
    --notes "Deterministic fixture, not real market data."

# Real historical data - the tool REFUSES to label this "historical"
# without all four provenance fields (provider, source, license, timezone).
python3 scripts/build_dataset_manifest.py datasets/historical/AAPL_2024-01-05.csv \
    --data-type historical \
    --provider "Your Data Provider" \
    --source-url "https://provider.example.com/downloads/AAPL_2024-01-05.csv" \
    --license "Internal research use; no redistribution" \
    --timezone "America/New_York" \
    --symbol AAPL --venue XNAS \
    --resolution "trade + top-of-book quote" \
    --notes "Every field is exactly as delivered by the provider; nothing was inferred."
```

The output is a JSON manifest (`<dataset>.manifest.json` by default)
containing a SHA-256 checksum, row count, schema version, timestamp range,
and every provenance field above. Store this manifest alongside the
dataset. `configs/*.yaml` experiment files should reference the dataset
path; the manifest is what a reviewer checks to confirm what that path
actually points to.

### Acquiring a real historical dataset

This repository's own tooling does not fetch market data from any
provider — that is a deliberate boundary (see `LIMITATIONS.md`), not a
missing feature to route around. To add one:

1. Obtain a small (single symbol, single session) file from a provider you
   have rights to use (examples: a broker's trade-history export, a paid
   tick-data vendor, a free-tier historical API you already have access
   to). Record exactly where it came from.
2. Convert it to the schema in this document (`timestamp_ms, last, bid,
   ask, bid_size, ask_size, volume`, optionally `bar_volume`, `bid_depth`,
   `ask_depth`). Do not invent any column the provider didn't supply —
   leave it out rather than guessing.
3. Run `scripts/build_dataset_manifest.py` with `--data-type historical`
   and the provenance flags. Fix every validation issue it reports.
4. Commit the CSV under `datasets/historical/` and its manifest next to it.
5. Point a `configs/*.yaml` experiment at the new path and re-run the
   determinism check from `BASELINE.md` §2 against it.

### Alpaca Historical Data (what was actually acquired, and its limits)

The codebase contains a working Alpaca ingestion pipeline
(`python/alpaca_historical.py`, `python/alpaca_adapter.py`, and the
`historical-execution/` Phase 2/3 scripts). It was run to produce the
bundled `datasets/historical/AAPL_2024-01-03_0930-1030ET.csv` from
**325,196 real IEX quotes** — so the *quote* path is functional and
exercised end-to-end. Its real limits, all reflected in that dataset's
manifest:

1. **Quotes were acquired; trade prints were not.** The acquiring
   environment had no `ALPACA_API_KEY`/`ALPACA_SECRET_KEY` and no network
   egress to Alpaca, so `historical-execution/download_trades.py` never
   ran. As a result `last` is the quote midpoint (not a real trade) and
   `volume` is `0` throughout — **POV cannot fill against this dataset**.
2. **Top-of-book only.** IEX quotes are L1; there is no L2/L3 depth.
3. **Single venue (IEX), not consolidated SIP/NBBO.**
4. **Resampled to one row per minute** after dropping ~15.5% of raw quotes
   flagged as outliers (see `historical-execution/normalize.py` and
   `inspect_outliers.py`), so intra-minute movement is not replayed.

**To add a dataset with real trade volume** (which POV needs), run the
`historical-execution/` download scripts with valid Alpaca credentials and
network access, then re-normalize and re-manifest. Always be honest in
`--resolution`/`--notes` about what the source actually provided — do not
label bar-level OHLCV as tick data.

## Market Data Normalization

The function `normalize_market_state(MarketState& state)` is applied to every record after parsing:

1. If `mid_price <= 0` and `bid > 0` and `ask > 0`, derive `mid_price = (bid + ask) / 2`.
2. If `last_price <= 0`, set `last_price = mid_price`.
3. If `bids` vector is empty but `bid > 0` and `bid_size > 0`, add a single level `{bid, bid_size}` to `bids`.
4. If `asks` vector is empty but `ask > 0` and `ask_size > 0`, add a single level `{ask, ask_size}` to `asks`.
5. Sync top-of-book: if `bids` is non-empty, set `bid = bids[0].price` and `bid_volume = bids[0].qty`.
6. Sync top-of-book: if `asks` is non-empty, set `ask = asks[0].price` and `ask_volume = asks[0].qty`.
7. If `mid_price` is still `<= 0` and `last_price > 0`, set `mid_price = last_price`.

## Validation and Error Handling

### File-Level Errors

| Error | Behavior | `CsvMarketSource::ok()` |
|-------|----------|----------------------|
| File not found | Load fails silently | Returns `false` |
| Empty file | No rows to read | Returns `false` |
| Malformed header | Required column missing | Returns `false` |

### Row-Level Errors

The table below reflects the actual behavior of `CsvMarketSource::load()`
in `src/market_data.cpp` as of this document's last update (verified by
reading the implementation, not assumed from the header comment):

| Error | Behavior | Recovery |
|-------|----------|----------|
| Malformed numeric field (parse throws) | Exception caught; all states cleared, load aborted | `ok()` returns `false` |
| Duplicate timestamp | Rejected during the load loop (`timestamp_ms <= last_timestamp_ms` check) | `ok()` returns `false` |
| Non-monotonic / backward timestamp | Same check as above — duplicates and backward steps are both rejected, not silently reordered | `ok()` returns `false` |
| Invalid bid/ask (`bid > ask`) | Explicitly checked per row during load | `ok()` returns `false` |
| Non-finite price (`last`/`bid`/`ask`) | Explicitly checked with `std::isfinite` | `ok()` returns `false` |
| Non-positive price | Explicitly checked (`<= 0.0`) | `ok()` returns `false` |

Note the file is **not** sorted after loading — timestamps must already be
strictly increasing in the source file, and the loader fails fast rather
than silently reordering rows, since reordering would hide a genuine data
problem. All of the above are also checked independently, before this
loader ever runs, by `scripts/build_dataset_manifest.py` (§ Data
Provenance above), which reports every problem row rather than aborting
at the first one.

### Recommended Handling

When `CsvMarketSource::ok()` returns `false`:

```cpp
CsvMarketSource source("datasets/sample_synthetic.csv");
if (!source.ok()) {
    std::cerr << "Failed to load market data. Check:\n"
              << "  - File exists: datasets/sample_synthetic.csv\n"
              << "  - Required columns present: timestamp_ms, last, bid, ask, ...\n"
              << "  - All rows have valid numeric values\n"
              << "  - Prices are finite and non-negative\n"
              << "  - Timestamps are monotonically increasing\n";
    return 1;
}
```

## Limitations

See `LIMITATIONS.md` for the complete, current list. The dataset-specific
ones are summarized here for convenience:

### Depth is limited to what the CSV provides

- Typically 1–3 levels (whatever `bid_depth`/`ask_depth` contain).
- No full L2/L3 order-book reconstruction from raw tick data.

### No Trade-by-Trade Tick Data

- Each CSV row represents a market event or bar, not individual trades.
- Trade prices and quantities are inferred from bar midpoints and volumes.
- True trade-by-trade execution simulation requires a different data model - see LIMITATIONS.md.

### Volume Interpretation

- `volume` is cumulative session volume, not incremental bar volume.
- `bar_volume` (optional) is the incremental volume for this bar/event only.
- The matching engine does not enforce volume constraints; it matches against submitted limit orders.

### Timestamp Units

All timestamps are in **milliseconds since Unix epoch**. Sub-millisecond precision is not supported. If your data is in seconds or microseconds, convert before loading:

```python
# Convert from seconds to milliseconds
df['timestamp_ms'] = (df['timestamp_sec'] * 1000).astype(int)

# Convert from microseconds to milliseconds
df['timestamp_ms'] = (df['timestamp_us'] // 1000).astype(int)
```

## How to Generate / Provide Your Own Dataset

### 1. Prepare CSV with Required Columns

```python
import pandas as pd

# Load or generate your data
df = pd.DataFrame({
    'timestamp_ms': [1000, 2000, 3000, ...],
    'last':         [100.01, 99.99, 99.97, ...],
    'bid':          [100.0, 99.98, 99.96, ...],
    'ask':          [100.02, 100.0, 99.98, ...],
    'bid_size':     [212, 252, 416, ...],
    'ask_size':     [579, 546, 216, ...],
    'volume':       [120, 359, 416, ...],
})

# Save
df.to_csv('datasets/my_data.csv', index=False)
```

### 2. (Optional) Add Depth Information

```python
# Create depth columns as pipe-delimited strings
df['bid_depth'] = df.apply(lambda r: f"{r['bid']}:{r['bid_size']}|{r['bid']-0.01}:{r['bid_size']//2}", axis=1)
df['ask_depth'] = df.apply(lambda r: f"{r['ask']}:{r['ask_size']}|{r['ask']+0.01}:{r['ask_size']//2}", axis=1)

df.to_csv('datasets/my_data.csv', index=False)
```

### 3. Validate

```python
from executor import CsvMarketSource

source = CsvMarketSource('datasets/my_data.csv')
if source.ok():
    print("Data loaded successfully")
else:
    print("Data load failed; check schema and values")
```

### 4. Run Experiment

```bash
# Update configs/example_experiment.yaml
sed -i 's|datasets/sample_synthetic.csv|datasets/my_data.csv|' configs/example_experiment.yaml

python3 python/run_experiment.py configs/example_experiment.yaml
```

## Reproducibility

**All data sources (CSV, synthetic, vector) produce deterministic results when replayed.** There is no randomness anywhere in this pipeline:

- ✓ Market data is fixed
- ✓ Strategies (TWAP, VWAP, POV, Adaptive) are deterministic
- ✓ Matching engine is deterministic
- ✓ Cost model is deterministic

**Replaying the same dataset + config twice produces identical `ExecutionResult`.**
