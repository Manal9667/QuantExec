# Project Completion Roadmap

## 1. Purpose

This document defines the work required to move the repository from a working execution-engine prototype to a complete, evidence-backed historical execution research platform.

The project already has a functioning C++ order book, matching engine, deterministic replay path, TWAP/VWAP execution logic, cost analytics, Python bindings, backend persistence, and a frontend dashboard. The remaining work is primarily about data credibility, replay fidelity, experiment rigor, and reproducible reporting.

The target is not an exchange simulator or a live broker. The target is a trustworthy research system that can answer:

> Given the same historical market conditions, how would different execution algorithms have executed the same parent order, and why did their results differ?

---

## 2. Current Baseline

### Already working

- C++ order book and price-time matching logic
- Market and limit order execution
- CSV market-state loading and validation
- Deterministic replay with time-window and seeking support
- TWAP and VWAP execution strategies
- POV, latency, cost, and impact extensions present in the current codebase
- Side-aware execution analytics for buy and sell orders
- Fill tracking, average execution price, slippage, implementation shortfall, and fill rate
- Transaction-cost calculations for commission, exchange fees, fixed fees, and spread estimates
- pybind11 boundary for Python orchestration
- FastAPI and SQLite experiment persistence
- React/Vite dashboard build
- C++ regression tests and Python backend tests
- Deterministic synthetic fixture for repeatable engineering tests

### Current limitations

- The default dataset is synthetic, not a verified historical market-data sample.
- The active replay input is normalized snapshots rather than a fully formal event stream.
- The market model is single-symbol and simplified.
- Queue position, cancellations, hidden liquidity, venue routing, and full L3 reconstruction are not modeled.
- Cross-session statistical comparison is not yet a complete reporting workflow.
- Benchmark numbers need documented hardware, workload, methodology, and memory measurements.
- Phase 2 service and dashboard code exists, but production readiness and live-trading safety are outside the current completion target.

---

## 3. Completion Strategy

Complete the project in the following order. Do not start with live trading or machine learning. Each stage should produce a verifiable artifact and a passing check before the next stage begins.

---

## Stage 0: Freeze and Record the Working Baseline

### Problem

The repository has many active files and several phases of work. Without a recorded baseline, later changes can make it difficult to prove whether a regression came from the data model, replay engine, strategy logic, or dashboard.

### Solution

Create a reproducible baseline record before adding new functionality.

### Steps

1. Configure and build the C++ project in Release mode.
2. Run the complete CTest suite.
3. Run the backend Python tests with discovery.
4. Build the frontend with `npm run build`.
5. Run the example experiment twice using the same configuration.
6. Save the resulting configuration, dataset identifier, fill summary, cost summary, and output hash in a baseline report.
7. Record the compiler, Python version, operating system, and CPU information.

### Acceptance criteria

- All configured C++ tests pass.
- All backend tests pass.
- The frontend production build succeeds.
- Two identical experiment runs produce identical results.
- The baseline report can be regenerated by another developer.

### Validation commands

```powershell
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
python -m unittest discover -s backend/tests -v
Push-Location frontend; npm run build; Pop-Location
python python/run_experiment.py configs/example_experiment.yaml
```

## Stage 1: Establish Real Dataset Provenance

### Problem

Synthetic data proves that the code is deterministic, but it cannot prove that the execution model behaves credibly under real market conditions. The current project therefore cannot yet make strong historical-performance claims.

### Solution

Add one small, legally usable, documented historical dataset while keeping the synthetic fixture for unit tests.

### Steps

1. Choose one symbol, one venue, one trading day, and one narrowly defined time window.
2. Record the provider, dataset URL or acquisition method, license or usage terms, timezone, symbol, venue, and acquisition date.
3. Record the source resolution: trade, quote, bar, L2 snapshot, or another format.
4. Store the raw file outside the repository when licensing requires it.
5. Store a normalized, redistributable sample or a checksum and acquisition script in the repository.
6. Convert source records to the project CSV schema without inventing unavailable fields.
7. Mark inferred fields explicitly. For example, a bar close must not be described as a true last trade, and missing depth must not be represented as real depth.
8. Add a dataset manifest containing row count, start time, end time, symbol, source, schema version, and SHA-256 checksum.
9. Add a validation command that rejects malformed, duplicated, non-monotonic, or inconsistent records.
10. Keep `datasets/sample_synthetic.csv` as the deterministic test fixture and label it clearly as synthetic.

### Acceptance criteria

- A reviewer can identify where the real sample came from and what each field means.
- The loader passes the real sample without silently sorting or repairing invalid data.
- Missing information is represented as missing rather than fabricated.
- The same source data produces the same normalized output and checksum.
- Documentation distinguishes synthetic tests from historical-data demonstrations.

### Deliverables

- `datasets/manifest.yaml`
- A documented acquisition or conversion script
- A normalized historical sample or reproducible download instructions
- Dataset validation tests
- Updated `dataset.md` and README data-provenance sections

## Stage 2: Formalize the Replay and Event Model

### Problem

The current system replays normalized `MarketState` snapshots effectively, but the architecture does not yet clearly separate raw market events, normalization, replay timing, and execution consumption.

### Solution

Introduce a small, explicit replay boundary while preserving the existing snapshot path for compatibility.

### Steps

1. Define the supported event types: quote update, trade, book snapshot, and session marker as needed by the chosen dataset.
2. Define a canonical `MarketEvent` containing timestamp, symbol, event type, source metadata, and event payload.
3. Implement a parser that converts source records into ordered `MarketEvent` values.
4. Implement a normalizer that converts events into the `MarketState` consumed by execution logic.
5. Define the behavior for missing quotes, crossed markets, duplicate timestamps, out-of-order records, and session boundaries.
6. Make replay controls explicit: start time, end time, `seek`, `next`, current timestamp, and end-of-stream state.
7. Ensure execution cannot read future events or future volume when making a decision.
8. Retain a snapshot adapter so existing tests and experiments continue to work during migration.
9. Add tests for replay boundaries, seeking, event ordering, and no-lookahead behavior.

### Acceptance criteria

- Raw input, normalization, replay, and execution are separate testable layers.
- The replay engine produces the same state sequence for the same input.
- A strategy only sees data at or before the current event timestamp.
- A requested time window excludes records outside its bounds.
- Existing deterministic tests remain green after migration.

### Deliverables

- Explicit event and replay interfaces
- Snapshot compatibility adapter
- Event-order and no-lookahead tests
- Replay documentation with a state-transition example

## Stage 3: Make Execution Realistic Enough for Research

### Problem

The current matching model is useful but simplified. It does not fully model the uncertainty between displayed liquidity and the quantity an order can realistically receive.

### Solution

Add realism incrementally, with each assumption exposed in configuration and validated by tests.

### Steps

1. Document the current fill assumptions before changing them.
2. Distinguish displayed top-of-book liquidity from simulated participant liquidity.
3. Add configurable partial fills when displayed quantity is insufficient.
4. Add order lifetime and cancellation behavior.
5. Add a deterministic queue-position approximation, or explicitly label the model as pro-rata/immediate liquidity if queue modeling is not supported.
6. Apply latency consistently to order submission and market-state visibility.
7. Define how market impact is estimated and ensure it is not confused with observed slippage.
8. Add stress fixtures for wide spreads, thin liquidity, price gaps, zero volume, and incomplete depth.
9. Test buy and sell symmetry for fills, slippage, spread cost, and implementation shortfall.

### Acceptance criteria

- Every realism assumption appears in configuration or documentation.
- Partial fills and unfilled quantities are represented correctly.
- Latency cannot create fills using information unavailable at submission time.
- Buy-side and sell-side metrics have correct signs and interpretation.
- Impact, spread cost, fees, and market movement are reported separately.

### Deliverables

- Execution-model specification
- Configurable fill and latency assumptions
- Adversarial liquidity fixtures
- Regression tests for both order sides

## Stage 4: Complete Strategy Comparison Experiments

### Problem

A single successful run does not demonstrate that one strategy is better than another. Strategies must be compared on the same parent order, data window, arrival price, cost model, and liquidity assumptions.

### Solution

Build a reproducible experiment matrix and report distributions rather than isolated results.

### Steps

1. Define a common experiment schema: symbol, side, quantity, time window, arrival price, limit policy, costs, latency, and dataset checksum.
2. Run TWAP, VWAP, POV, and a simple immediate-execution baseline where supported.
3. Use identical market inputs and parent-order parameters for every strategy.
4. Repeat across multiple sessions, symbols, order sizes, and market regimes when data permits.
5. Record completion rate, average price, implementation shortfall, spread cost, explicit fees, participation rate, time-to-completion, and unfilled quantity.
6. Report mean, median, standard deviation, percentiles, and failure/completion counts.
7. Add a deterministic result ID based on configuration and dataset checksum.
8. Export machine-readable JSON or CSV alongside the human-readable report.
9. Add a clear statement that backtest results are not guarantees of live performance.

### Acceptance criteria

- Every strategy receives identical conditions within a comparison group.
- Results can be regenerated from the stored configuration and dataset manifest.
- Reports include both central tendency and dispersion.
- Failed or incomplete executions are not silently dropped.
- The dashboard and API show the same values as the batch experiment output.

### Deliverables

- Experiment schema and version
- Batch comparison runner
- JSON/CSV report output
- Multi-session comparison fixtures
- Dashboard comparison view backed by persisted results

## Stage 5: Make the Backend and Dashboard Reliable

### Problem

The backend and frontend provide useful experiment visibility, but the project is not complete until they expose provenance, assumptions, errors, and comparable results consistently.

### Solution

Treat the API and dashboard as research reproducibility tools rather than merely visual wrappers.

### Steps

1. Validate experiment configuration at the API boundary.
2. Return explicit states for queued, running, completed, failed, and cancelled experiments.
3. Persist the dataset checksum, code/config version, strategy parameters, and model assumptions with every result.
4. Return structured validation errors instead of generic failures.
5. Add pagination or bounded queries for experiment history.
6. Ensure repeated submission behavior is defined and tested.
7. Display strategy assumptions, data provenance, fill completion, and cost decomposition in the dashboard.
8. Add loading, empty, error, and partial-result states.
9. Add API tests for invalid configs, missing datasets, failed runs, and result consistency.
10. Add a frontend smoke test or browser validation for the primary experiment workflow.

### Acceptance criteria

- An experiment result is understandable without opening the source code.
- Failed runs explain what failed and retain enough metadata to reproduce the issue.
- API and dashboard values match the engine output.
- The UI clearly labels synthetic versus historical data.
- No endpoint claims live trading capability unless a separately validated connector exists.

## Stage 6: Benchmark and Quality-Gate the System

### Problem

Current benchmark output is useful as a smoke check but is not yet sufficient for performance claims.

### Solution

Define a repeatable benchmark protocol and make it part of release validation.

### Steps

1. Define workloads by event count, depth, order size, strategy, and number of fills.
2. Run benchmarks in Release mode on a recorded machine configuration.
3. Separate parsing, replay, matching, strategy, analytics, and Python-boundary timings.
4. Measure memory usage for representative datasets.
5. Run warm-up iterations and multiple measured iterations.
6. Report median and percentile timings, not only one run.
7. Record compiler, build flags, operating system, CPU, and dataset checksum.
8. Add regression thresholds for catastrophic performance changes.
9. Run the full quality gate before calling a milestone complete.

### Quality gate

```powershell
cmake --build build --config Release
ctest --test-dir build -C Release --output-on-failure
python -m unittest discover -s backend/tests -v
Push-Location frontend; npm run build; Pop-Location
build\Release\benchmark.exe
python python/run_experiment.py configs/example_experiment.yaml
```

The exact benchmark path may differ by generator or platform; the release report must record the command actually used.

### Acceptance criteria

- The benchmark is reproducible and its methodology is documented.
- No test, build, or experiment command depends on undeclared local state.
- Performance regressions are visible in CI or release reports.
- Documentation reports measured facts rather than unsupported estimates.

## 4. Definition of Complete Project

The project can be described as complete for its intended research scope when all of the following are true:

- A real historical sample has documented provenance and a reproducible normalization process.
- Synthetic data remains available for deterministic unit and regression tests.
- The replay boundary clearly separates input events, normalization, time progression, and strategy decisions.
- No-lookahead behavior is tested and demonstrated.
- Execution assumptions are explicit, configurable, and covered by buy/sell tests.
- Multiple strategies are compared under identical conditions across more than one session or market regime.
- Results include fills, completion, slippage, implementation shortfall, explicit fees, spread, impact assumptions, and uncertainty statistics.
- Every result stores its dataset and configuration identity.
- The API and dashboard expose the same reproducible result and its limitations.
- C++ tests, Python tests, frontend build, example experiment, and benchmark quality gates pass.
- README and status documents describe exactly what is implemented and do not imply live-trading or production-grade capability.

At that point, the project is a complete historical execution research platform for its declared scope. It still would not automatically be a production trading system; live deployment would require separate operational, risk, compliance, connectivity, and safety work.

---

## 5. Recommended Order of Work

1. Freeze the current green baseline.
2. Add dataset provenance and a small real historical sample.
3. Formalize the event/replay boundary without breaking the snapshot adapter.
4. Strengthen fill, latency, and no-lookahead behavior.
5. Build multi-session strategy comparisons and statistical reports.
6. Connect those reports to the backend and dashboard.
7. Document and automate benchmark and release quality gates.
8. Update README, dataset documentation, and phase status only after each acceptance gate passes.

This order keeps the project honest: data credibility comes before performance claims, replay correctness comes before strategy comparisons, and strategy comparisons come before dashboard conclusions.
